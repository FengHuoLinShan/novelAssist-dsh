# dsh-rebuild 实施方案(草案, 随 ADR 确认后细化)

## 0. 决策前提

- ADR-0014 通过后启动 Phase A; 未通过前只做盘点与文档。
- 所有改动在 worktree(/Users/tywww/Desktop/项目/ai-writing-assist-dsh-rebuild)的
  dsh-rebuild 分支; 主工作区不触碰。

## 1. Phase A — 侧车骨架 + 试点工作流(est. 2-3 轮)

1. dsh-sidecar/ 目录: Node 工程(pnpm + tsdown 或 tsc), 依赖 @deepseek-ai/dsh 锁定 rc.6。
2. 侧车服务: 每项目进程池(按 novel_id 派生 workspace 目录); 内部 HTTP 桥
   (POST /internal/runs/{task_id}/start, POST /internal/runs/{task_id}/progress,
    POST /internal/runs/{task_id}/finalize, GET /internal/runs/{task_id}/health)。
3. FastAPI 侧: infrastructure/tasks 增加 DSH executor(可配置开关
   TASK_EXECUTOR=pg|dsh-sidecar, 默认 pg, 灰度切换), internal 端点 + service token。
4. managed_llm_step 工具(权限枚举/schema/预算/超时/journal/provenance)。
5. 试点: outline_analyze 走侧车执行(handler 逻辑复用, 仅运输与 step 信封走侧车);
   验收: 同输入同输出(含审计 journal 字段), 模块测试全绿, mock LLM。

## 2. Phase B — 信封迁移的关键路径建设(重定义, est. 1-2 轮)

重定义(2026-08-14, 基于实机事实, 见 DECISIONS): 原"运输层替换"搁置——async_tasks(PG)
是数据语义与公开 API 契约的真相源, 替换领取/终态运输无等价收益且引入跨进程风险;
worker 仍由 Python 驱动, DSH 承载 step 信封。Phase B 交付:
1. **structured 回调扩展**(internal_llm_bridge 支持 schema_ref → 既有
   generate_structured 修复预算, 规格见 PhaseA-接线规格.md §3.5)——26 个
   run_managed_* 调用点中 85% 是 structured, 这是 Phase C 的前提。
2. **dsh-sdk 灰度开关面**: 配置级 executor 已就绪; 补启动自检(池/运行时可及性
   探测, 失败 fail-closed 且错误文案可读)与 worker 侧池生命周期验收。
3. 每组验收: infrastructure/llm + 该模块工作流测试 + mock 端到端(runbook)。

## 3. Phase C — step 信封迁移(est. 4-6 轮)

- 34 个工作流按对照清单 §3.3 逐行迁移; 每个工作流:
  迁移 → 模块测试 + prompt-contracts + 预算/超时/审计字段对比 → 对照清单 §6 回填。
- 流式特例: interaction_story_generate(SSE + 512字符/2s checkpoint)单独设计
  (侧车流式回调桥接), 最后迁移。

## 4. Phase D — agent 产品面(est. 2-3 轮)

- workflow 模板(批量审校/导入复核); 可选 client-plugin(需 DSH 源码 checkout)。
