## 4. 模型分工(编排脑 / 内容手)

【已确认 D2】

| 面 | 模型 | 连接来源 | 职责 |
|---|---|---|---|
| 编排脑 | deepseek-v4-flash, high effort | 账户级连接(用户在 DSH 侧保存) | 观察/计划/验证/复核/分组/对话; 便宜、快、可大规模 fan-out |
| 内容手 | 用户自定, **经 DSH 切换 + 多模型预设(D13)** | DSH credentials(Key 不落盘); M1/M2 过程形态才走项目快照/内部桥 | 切分/语义补全/融合判断/实体别名关系/结构分析 |

- **质量红线**: 正文与抽取质量只由内容手(冻结快照模型)决定, 编排脑推理不承载内容质量。
- **交叉验证红利**: 验证者(flash)与生成者(内容模型)不同族, 交叉检查优于同模型自查;
  代价是 flash 易幻觉 → 每个验证子代理必须走 workflow 强制 schema 输出, 不许自由文本汇报。

## 5. 核心转变: 从流水线到目标循环

【提案】

旧: `deep_import` 一个任务跑到底, 内部质量门是代码常量, 产出丢进 UI 待处理区由作者事后翻。
新: 整个导入是一个 DSH `goal`, 每轮 agent 跑同一循环:

```
观察(read_* / 读 checkpoint)
 → 判断(下一步: 计划偏差/质量缺口/待处理堆积/作者新指令)
   → 行动(workflow fan-out 内容步 / 子代理验证 / merge)
     → 验证(质量门 + 交叉检查)
       → 对话(作者语言汇报, 请求确认或方向)
         → 记忆(checkpoint + set_progress) → 下一轮
```

| 维度 | 旧流水线 | 新目标循环 |
|---|---|---|
| 启动 | 填参数 → 授权快照 → 全量跑 | 对话协商目标 → 计划批准 → 增量推进 |
| 粒度 | 章区间整体 | 每章/每批次可独立重跑(「第 7 章重切」是一等操作) |
| 质量门 | 代码阈值 | 验证子代理 + policy.yml 硬阈值(policy-as-data) |
| 复核 | 作者去待处理区翻 | 对话式 triage + 智能分组 + 批量批准 |
| 失败 | 固定降级 + resume/abandon | 降级条款进 policy + ralph 修复环 + goal 续跑 |
| 终点 | 任务 done | 转入守望(第 7 节) |

## 6. 深度导入六阶段重设计

【提案】

- **Stage 0 · 摄入**: 零 LLM。解析文件 → 章节落地(parsers/chapter_loader 确定性原语)。
  agent 只读汇报(章数/字数/结构)。
- **Stage 1 · 意向**: 纯编排脑。`read_project_state` → 与作者协商目标(全量/只世界/只结构;
  补导入还是重切) → **成本预告**(约 N 个内容步、M 批、预算 X tokens, 作者语言)
  → 一次计划批准 → `begin_import(plan_id)` 落授权记录。
- **Stage 2 · 地图**: 章节地图(确定性) → `compile_phase1a_context`(保留的确定性 helper)
  → 切分 fan-out(`pipeline(章节批次)`, 每子代理: read_chapters → llm_step(scene_slicing,
  schema=SceneCandidates) → stage_candidates(scenes)) → `parallel` 验证子代理核验覆盖/锚点/
  连续缺口 → **对话点**: 作者可对单章打回重跑(ralph 修批环) → `adopt(scenes)` 走引擎
  fenced Scene commit 原语(CAS/deprecation/覆盖裁决全保留——数据完整性, 非策略)。
- **Stage 3 · 世界**: 见 §6.1 去重管道 + 别名附着 + 对话式 triage。
- **Stage 4 · 结构**: 确定性上下文编译(原语) → 单次 llm_step(structure)(内容手此时最吃
  质量) → stage_candidates(structure) → 提案 → 确认/编辑 → adopt。
- **Stage 5 · 守望**: 见 §7, 升格为助手存在形式。

### 6.1 去重管道 L0–L4

【已确认 D4】

> 哲学: 在「合并可逆」的前提下, **去重越激进越好**——宁可多合(少量失误), 不可漏合。
> 成功度量: 确认项数 = f(去重率, 失误率); 目标是把待确认项压到旧流程一个数量级以下。
> **激进度 = L1 合并判定的置信门槛**(policy.yml 的 `dedup.merge_bias / l2_threshold`):
> 激进 = 门槛低、宁可多合(可逆, L4 修复); 保守 = 门槛高、多留待确认。默认激进,
> 不设显式拨杆(D18), 自然语言可临时调整。

| 层 | 做什么 | 谁执行 | 可逆性 |
|---|---|---|---|
| L0 | 名字归一化、同 Scene 同名同型合并、既有确定性规则 | 引擎原语(复用 deep_import_dedup) | 天然 |
| L1 | 全部候选按归一化名分组, 组内判同一/不同(带来源 Scene 证据 + 置信度) | 编排脑(flash, 大规模初判) | 提案 |
| L2 | 仅对 L1 低置信组二判 | 内容手(llm_step(dedup_judge)) | 提案 |
| L3 | merge_candidates(CAS) 执行; 结果压缩成一张报告, 分组一次批准 | 引擎 + DSH approval | merge 记录 + split |
| L4 | 用户指出误合/漏合 | 自然语言 → 微工作流(§10) | 同上 |

**去重报告**(用户只确认一遍):

```
本次导入(第 1–10 章)
  抽取候选 128 个 → 自动合并为 34 个实体
  ✓ 高置信合并 87 次(跨 Scene 合并 12 次, 证据可展开)
  ⚠ 不确定 5 组(每组带来源 Scene + 分歧点, 排最前)
  ▸ 一次批准全部高置信合并 ▸ 逐组确认不确定项
```

风险前移(最可能错的排最前); 批准一次 approval 携带合并清单摘要; 拒绝/失败 fail-closed;
作者纠正后 agent 只重呈增量。

**可逆合并语义**(引擎新增面, 量小): 候选态合并免费可逆; 已采用合并新增 `merge_records`
(source_ids → target_id、provenance、workflow、可回滚标记), merge 不删 source(历史状态
优先); 新原语 `merge_entities / split_merge / attach_alias`。复用现有
`/api/world/entities/fusion-suggestions`(已在插件白名单)作为机制底座, 新去重是它的
规模化+激进版。

## 7. 助手升格: 六个雷达面

【已确认 D3/D5】

| 雷达 | 持续做什么 | 信号示例 | 现有映射 |

| 剧情 | 当前剧情状态摘要、进度感 | 「主角正处第 17 章·雨夜对峙, 距本卷高潮约 3 章」 | world.ask + outline 事实 |

| 写作 | 写作副驾驶持续监看: 当前章 vs 人物/地点/设定一致性、Scene 必发生项 | 「本 Scene 应有林晚在场, 正文未提及」 | SceneCockpit 信号 + semantic_reviews |

写作副驾驶形态: **实时面**(写作中, 确定性规则信号 = 现有 rail, 不动) + **异步面**
(章完成后 semantic_reviews/定向修订进雷达, 产出风险与修订提案进收件箱)。

## 9. 工作台与宠物(快速批判面)

【已确认 D5】

**宠物** = 助手在场感, 状态即信息:

| 宠物状态 | 含义 | 动作 |
|---|---|---|
| 静默 | 无新事 | 点击 → 一句话剧情摘要(默认答复) |
| 耳动/微光 | 有新信号(不打断) | 点击 → 收件箱弹出 |
| 忙碌 | 后台工作流在跑 | 悬停 → 进度 |
| 待确认 | 有需要裁决的项 | 角标数字 = 待确认数 |

**收件箱卡片**:

1. 首行是可执行命题, 证据折叠在下方;
2. 四个动词一排: `采纳 ✓ / 打回 ✗ / 改一改 ✎ / 先放着 ···`; 打回**必须可带一句话理由**
   (理由 = per-book 校准原料);
3. 风险前置排序: 冲突 > 风险 > 待确认 > 提示; 高置信可逆批量项压底;
4. 批量框选一次采纳; 全部动作有 undo 窗口;
5. 键盘流: j/k 导航、1/2/3/4 动词、u 撤销;
6. 窄屏: 宠物退化为角标, 收件箱变底部抽屉, 动词保留;
7. 「改一改」: 展开内联编辑或自然语言改(→ 微工作流生成修改提案再确认)。

**边界**: rail 继续做写作中实时参照(不合并); 宠物/收件箱管写作外的一切。

## 17. 写作台设计(副驾驶即主工作台)

【已确认 D8/D9/D10】

### 17.1 前提转变(对照原设计)

| | 原设计 | 新前提 |
|---|---|---|
| 文本流 | 应用内编辑器是第一视觉焦点, autosave/乐观锁/光标/离开恢复是核心工程 | 文本在 Word; 项目只做**停靠与版本**——文本流变成同步桥, 不是编辑会话 |
| 副驾驶角色 | 右侧 rail, 消费手选 Scene, 只做确定性警报(原设计明确「不会自动运行 AI」) | **主视觉区**, 兼做计划/参照/评审/雷达, AI 是第一公民 |
| 实时性 | 光标移动 → 现场信号 | Word 在右半屏, 没有光标; 「实时」= 版本同步后 + 写作中的扫视式参照卡 |

### 17.2 文本流: 停靠舱 + 同步循环

- **同步入口**(v1): ① 拖文件 → **DSH 网页原生接收** → 项目侧统一转换为 **.txt/.md** 入库
  【计划实现, D9a】; ② 复制粘贴 → 只识别文字, 同样落为 .txt/.md。**文件夹守望 v1 不做**
  (延后)。实现备注: DSH 官方 attachment seam 现文档为图像 v1(png/jpeg/webp/gif),
  文本附件接收通道实现时需实测核实。
- **每次同步 = 一个新版本**: M4 下版本 = git commit + frontmatter content_hash(§22.2);
  过程形态(M1/M2)才复用旧引擎 draft version 协议。历史/回滚语义由 git 白拿。
- **同步后连锁**: 差异识别(vs 上一版) → 受影响 Scene/信号自动过期 → 雷达重扫受影响章 →
  收件箱更新。
- **回 Word 方向**(v1): 修订提案给**可复制修订块**(逐条说明 + 修改后文本); 「导出带批注
  .docx」列为候选增强, 未定。

### 17.3 单屏分屏布局(D10)

默认左半 = DSH 网页, 右半 = Word。含义: **工作台按半屏宽度设计**, 不是第二块屏:

- 参照卡/收件箱/卡片全部半宽优先、纵向排布、扫视式大字号、键盘翻页;
- 宠物与收件箱在半宽下必须可用(角标 + 底部抽屉形态);
- DSH web 是主入口(宠物 UI 落点问题随之收敛到 DSH web, Vue console 角标可选)。

### 17.4 副驾驶工作台四模式

| 模式 | 是什么 | 核心内容 |
|---|---|---|
| 写作前 · 计划台 | 今天写什么 | 章节计划、Scene 地图、「下一步提案」2–3 条(各带依据/成本/风险, 作者选或拒) |
| 写作中 · 参照台 | 右半屏 Word 对面 | **章节参照卡**: 本 Scene 在场人物、地点、设定、必发生项、POV 规则、已种伏笔——一屏简报, 按章静态生成、按需刷新 |
| 写作后 · 评审台 | 同步即开 | 语义审查 + 冲突检查结果、修订提案(diff 预览)、信号卡片(四动词) |
| 守望 · 常驻 | 不写作时 | 六雷达 + 收件箱 + 宠物(§7–§9) |

### 17.5 解除「编辑器为王」后解锁的能力

1. **章节档案(Chapter Dossier)**: 每章一整页——Scene 分解、人物在场、POV、时间线位置、
   伏笔种下/回收对账、设定引用清单、节奏指标; 雷达持续刷新。
2. **剧情地图(Story Map)**: 原设计「统一叙事时间轴」被暂缓, 现升为主视图——章 × 线索 ×
   Scene 视觉时间线、主角当前位置、张力曲线、伏笔回收进度。
3. **下一步提案中心**: 「续写提案」微工作流常驻成面板; 基于 outline/memory/world 给下一章
   2–3 个方案, 选定即备好参照卡。
4. **修订中心**: semantic_reviews / targeted_revisions / 冲突修复变一等公民——卡片 + diff +
   一键可复制修订块。
5. **世界一致性台**: 「本章写完至今世界观变了什么」——新实体、被违反的设定、需回改旧章。
6. **写作健康**: 不刷屏的温柔指标——同步间隔(卡文检测)、章节密度、死线距离, 作者语言。

### 17.6 对话即工作台(与六雷达设计合流)

- 中列 = DSH 对话流(计划协商、打回理由、自然语言微工作流全在此发生);
- 制品 = 章节档案卡、信号卡、修订卡、剧情地图, 全部以卡片进对话流, 每张卡带动词;
- 收件箱与写作台是同一事物的两个视角: **收件箱 = 时间序, 写作台 = 章节序**(按章聚合的
  档案 + 地图)。

### 17.7 基本编辑能力边界(保留但做小)

- **必须有**: 粘贴停靠、文本查看、typo 级轻改、diff 预览、把 AI 修订应用到文本、候选只读、
  版本历史。
- **明确不做**: 复杂排版、多光标、富文本生态——Word 的地盘; 本项目编辑器是「文本停靠舱」,
  不是写作环境。

| chat 共创对话 | 世界观自由共创(温度 0.8); pro = 同模型二次审查; 不写资产 | 助手对话本身 + `llm_step(spec=world_creation_chat)`; pro = 内容手二次审查或编排脑交叉验证 |
| convergence 收束 | 对作者选定来源窗口只读汇聚, 不物化建议 | 「补设定」微工作流内部步: 汇聚 → 页面提案 |
| exploration 探索 | 只读给出至多 3 个一跳相邻世界缺口 | 建议雷达主动探测 → 「可探索缺口」卡片 |
| semantic-inspection 检修 | 检修冻结页面, findings 供复核 | 一致性雷达/世界一致性台 → 信号卡(四动词) |
| suggestions 建议 | typed 待处理建议(target: core_entity/world_bible_page/world_bible_new_page); apply-page-draft 重验后只写工作稿 | `stage_candidates(world_suggestion)` → 收件箱信号卡 → `adopt` + approval |
| ask-world 问世界 | 证据grounded问答, 证据不足拒答; 显式保存才生成 pending | 保留原语(插件已有 `novelcraft_ask_engine`) + 剧情雷达默认答复 |
| publish-impact 发布预演 | 发布前只读确定性引用影响预演 | 确定性只读原语 `read_impact` + 风险雷达发布前检查 |

**总原则**: 五个 LLM 模式从「并列 UI 模式」变为**编排脑按意图调用的内容手步骤**
(自然语言 → 意图路由 → llm_step(spec)), 入口从按钮变对话, 能力不减少。

**保留为底座(语义不变)**: M1/M2 下为引擎底座(快照冻结 + 内部桥); **M4 下由
`@novelcraft/world` + `@novelcraft/store` 按 Spec 重写**——快照语义 = `.assistant/llm.yml`
+ DSH credentials(§22.5); 页面/提示词模板 = llm_step 的 spec 资源; target 校验与 apply
前重验 = frontmatter + git 工作区检查; canonical 只经世界书发布; 建议队列 = pending/ 目录。

**注意**: 生成中心 chat 是既有 7 处有意直调点之一(功能对照清单 §6), 新设计中随所有
内容步一起走 llm_step/内部桥, 该尾项自然消解。

## 21. 开源分发与扩展性(单用户模式)

【已确认 D11】

### 21.1 单用户模式下的引擎形态

```
用户机器(docker compose up 一条命令)
 ├─ NovelCraft Engine(127.0.0.1, 单用户 appliance)
 │    ├─ ~16 个原语工具 + 管理面(HTTP + OpenAPI 契约)
 │    ├─ novel_id 隔离保留(一个人多本书仍需分区)
 │    └─ 账户/OIDC/owner 门禁全部裁剪
 └─ DSH(用户自己的 profile)
      └─ @novelcraft/dsh-plugin(npm, dsh plugin add)
           └─ 全部可扩展性在这里
```

**单用户裁剪清单**: account 模块退化为「本机 + 可选 token」; owner 双门禁删除; novel_id
过滤保留(多本书是数据分区, 不是多租户); 插件 authMode=none/bearer 已够用(三模式现成)。

### 21.2 三层扩展面(用户通过 DSH 改/加功能的三条路)

| 层 | 改什么 | 用户要做什么 | 兼容性影响 |
|---|---|---|---|
| 数据级(零代码) | policy.yml 阈值、prompt/spec 模板、页面模板、自定义实体类型(已是开放字符串) | 改文件 | 无 |
| 编排级(DSH 全开放, 主战场) | skills、presets、workflow 脚本、defineTool 插件、微工作流目录 | 写 DSH 插件/脚本, `dsh plugin add` | 无 |
| 引擎级(只给贡献者) | 新增原语 | 走仓库 PR + 契约门禁测试 | 契约版本递增 |

**核心结论**: 引擎的兼容性 = 原语契约稳定。只要 ~16 个原语的 HTTP 契约(带版本号, 插件已有
`contractVersion: v1`)不变, 用户在 DSH 层的任何折腾都不破坏兼容。兼容面小、稳定、可测试
(`dsh-plugin/test/mock-engine.mjs` 契约测试随开源发布, 用户插件可对同一份 mock 跑)。

### 21.3 分发形式

1. **引擎**: `docker compose up -d`(PG 单容器)为主; 可选 `pip install novelcraft-engine` +
   `nc-engine serve`(快启动路径)。
2. **指挥层**: `dsh plugin add @novelcraft/dsh-plugin` + 配置 `engineUrl`/`agentToken`。
3. **可选 MCP 面**: 引擎再暴露薄 MCP server(stdio/HTTP), 非 DSH 客户端(Claude Desktop 等)
   也能调原语; DSH 原生 mcp-client 现成, 工具名 `mcp__novelcraft__*`。
4. **模板仓库**: 开源 `novelcraft-starter`(docker-compose + 插件配置 + 示例 skills),
   新用户从 fork 开始而不是从零开始。

### 21.4 引擎「无聊化」原则

- 引擎只保留数据完整性原语(merge/adopt/CAS/schema/novel_id), 删除所有策略与 UI 逻辑;
- 契约版本化 + 语义化版本, 升级窗口显式;
- 用户加功能的默认答案永远是「在 DSH 层写插件/脚本」, 不是「改引擎」;
  引擎 PR 只收原语级新增。

## 22. M4 终态: 一切皆插件的彻底重写

【已确认 D12】

### 22.1 形态一句话

产品 = **DSH + @novelcraft 插件族 + 一个 profile bundle**。安装: `dsh plugin add
@novelcraft/*` → 开 DSH web → 说「新建一本书」→ 插件在 `~/Novels/<书名>/` 建文件夹 →
对话开始。没有独立引擎进程、没有数据库、没有独立前端。

### 22.2 文件夹真相(folder-as-truth)

```
~/Novels/<书名>/
  book.yml                    # 书名/题材/基调/规模(project)
  chapters/003.md             # 正文(draft, 用户 Word 写完同步进来)
  scenes/*.md                 # Scene 资产(frontmatter: id/status/chapter_ids/evidence)
  world/objects/*.md          # 已采用实体(canonical)
  world/pending/*.md          # 待处理候选(frontmatter: status/evidence/confidence)
  structure/threads.md arcs.md foreshadowing.md
  memory/events.jsonl         # 事件溯源
  bible/*.md                  # 世界书页面(frontmatter status: draft/canonical)
  imports/*.md                # 导入原文停靠(D9a: 统一 .txt/.md)
  .assistant/policy.yml       # 策略即数据(§13)
  .assistant/calibration.md   # per-book 校准笔记
  .assistant/checkpoint.json  # 编排状态
  .assistant/signals/*.json   # 收件箱信号
  .assistant/llm.yml          # 内容手 provider/model/参数(Key 不进文件)
```

**90 表语义 → 文件/git 映射**:

| 旧语义 | M4 落法 |
|---|---|
| revision / CAS | git: 已采用资产每次 adopt = 一个 commit; content_hash 进 frontmatter; 工作区脏时拒绝 adopt |
| 已采用不硬删除 | git 历史天然保留; 删除 = 新 commit 移除 + 墓碑文件 |
| 待处理状态机 | `world/pending/*.md` + frontmatter status; adopt = 移入 canonical + 一次 commit(原子) |
| 别名不建新对象 | object frontmatter `aliases: []` |
| 世界书 draft/canonical | bible frontmatter status; 发布 = adopt+commit; publish-impact = 只读插件 |
| suggestion queue | pending/ 目录即队列 |
| 关系/反向关系 | relations 索引(可重建) |
| import_records | imports/*.md + import-log.jsonl |
| async_tasks / 进度 | session log + checkpoint.json + DSH jobs(长任务) |
| novel_id 隔离 | 每书一个文件夹 + 每书一个 DSH session; scope 子系统做会话内分区 |

**索引规则(关键)**: 文件是唯一真相; sqlite domain KV(`ctx.storage`)只是**派生索引**
(别名查找/关系图/覆盖率), 任何时刻可全量重建(`store rebuild-index`)。用户手改文件后
跑一次重建即一致——完美契合「用户在 DSH 里直接改文件」的哲学。

  - **改造平移**: `dsh-plugin/host` 8 工具的设计文档价值保留, 实现按 §22.3 插件族重切。

## 24. R0 Spec 提取规格与 frontmatter 草案

【提案】

### 24.1 R0 三份产出

1. **资产 schema 目录**(`specs/assets/`): 每类资产的 frontmatter 字段/类型/必填/状态机
   (book/scene/object/pending/chapter/thread/arc/bible-page/memory-event);
2. **prompt/spec 目录**(`specs/prompts/`): 从 `docs/prompts` 与旧代码 prompt 常量提取
   llm_step 的 spec 资源(scene_slicing/enrich/fusion/entity_extraction/alias_relation/
   structure/dedup_judge/world_creation_chat...), 每份含 output_schema + 预算 + 温度;
3. **规则目录**(`specs/rules/`): merge/去重规则、CAS 检查、世界书 lifecycle、降级条款
   → `policy.yml` 默认值 + `@novelcraft/store` 完整性规则清单。

### 24.2 frontmatter 草案(示例)

```yaml
# book.yml
title: 诡秘之主
genre: 克苏鲁/蒸汽朋克
tone: 悬疑
target_length: epic
current_stage: writing

# world/objects/克莱恩-莫雷蒂.md
---
id: obj_klein
kind: character
status: canonical
aliases: [周明瑞, 愚者]
evidence:
  - source: chapters/003.md
    quote: "……"
workflow: import-deep@2026-08-14
adopted_at: 2026-08-14T10:00:00Z
---

# world/pending/红衣女子.md
---
id: pend_red
kind: character
status: pending
confidence: 0.62
evidence: [{source: chapters/007.md, quote: "……"}]
suggested_action: merge_with(obj_klein)
---

# scenes/s012.md
---
id: s012
status: canonical
chapter_ids: [7, 8]
summary: 雨夜对峙
characters: [obj_klein, obj_suwan]
must_happen: [身份暴露]
content_hash: sha256:…
---
```

规则: `status` 只在 canonical/pending 间经 adopt 迁移; `content_hash` 随每次内容变更
更新; provenance 引用 session log 序号 + 证据原文引用, 双向可追溯(§22.4)。

## 25. 全局完成定义(DoD)与风险回滚

【提案】

### 25.1 全局 DoD

- M4 产品可用: `dsh plugin add @novelcraft/*` 后, 新用户不接触任何旧仓库概念即可
  「新建书 → 拖 Word 文件 → 深度导入 → 复核去重报告 → 写作中参照 → 修订 → 守望」全链跑通;
- 数据语义等价: 对 R0 Spec 的每条规则有对应行为契约测试(§15);
- 编排纪律: trace contract 全绿; adopt 必过 approval; 信号新鲜度生效;
- 开源面: `novelcraft-starter` 一键安装 + mock 测试面随包发布(§21);
- 旧引擎退役: R4 后旧 FastAPI/PG 不再被任何路径依赖, 旧仓库归档为 Spec。

### 25.2 风险与回滚

| 场景 | 回滚 |
|---|---|
| R0–R3 失败 | 退回 M1/M2(HTTP/MCP 挂载旧引擎), 零损失(§16) |
| 单书数据错误 | 每书一个 git 仓库: adopt 可 revert, 全量历史可回看 |
| 插件缺陷 | 插件独立版本化, 回退单个 npm 包; store 规则由 Spec 契约测试锁死 |
| DSH rc 升级破坏 | 锁定 seam 依赖清单(§22.7) + 升级窗口 + 契约门禁重跑 |
| 编排脑幻觉失控 | 验证子代理强制 schema; policy 轮数/预算上限; 写正史 approval fail-closed(§11) |
